LexPercent Pro
Техническое задание
Версия: 1.1 от 08.09.2026
Статус: Утверждено заказчиком

1. Общие положения
1.1. Наименование программы
LexPercent Pro — настольное приложение для автоматизированного расчета процентов за пользование чужими денежными средствами, подготовки расчетов в форме официальных документов и формирования сопроводительной документации.

1.2. Назначение программы
Программа предназначена для автоматизации выполнения расчетов процентов за пользование чужими денежными средствами в соответствии с требованиями гражданского законодательства Российской Федерации.
Программа должна обеспечить:
выполнение математически корректного расчета процентов;
учет изменения ключевой ставки Банка России;
учет начислений задолженности;
учет произведенных оплат;
автоматическое разделение расчетного периода на интервалы;
подготовку официального документа «Расчет процентов»;
формирование подробного протокола произведенного расчета;
возможность повторного открытия и изменения любого проекта.

1.3. Основные принципы
При разработке программы должны соблюдаться следующие принципы.
1.3.1. Приоритет корректности
Абсолютным приоритетом программы является математическая корректность расчета.
Скорость выполнения расчета, удобство интерфейса и иные характеристики не могут иметь преимущество перед правильностью результата.

1.3.2. Повторяемость результата
При одинаковых исходных данных программа всегда должна формировать абсолютно идентичный результат.
Повторный расчет не должен зависеть:
от даты запуска программы;
версии операционной системы;
локальных региональных настроек;
времени суток;
компьютера пользователя.

1.3.3. Прозрачность расчета
Любой результат должен быть полностью проверяемым.
Для каждого расчетного периода пользователь должен иметь возможность определить:
дату начала периода;
дату окончания периода;
количество календарных дней;
размер задолженности;
действующую процентную ставку;
математическую формулу;
размер начисленных процентов.

1.3.4. Неизменность математического алгоритма
После утверждения алгоритма расчета изменения математического ядра допускаются исключительно при:
обнаружении ошибки;
изменении законодательства;
утверждении новой версии программы.
Любые изменения алгоритма должны фиксироваться в журнале изменений проекта.

1.3.5. Разделение ответственности
Программа должна быть разделена на независимые уровни.
Уровень предметной области (Domain)
Содержит исключительно описание предметной модели.
Не содержит пользовательского интерфейса.
Не содержит кода формирования документов.
Не содержит работы с файлами.

Уровень математического ядра (Core)
Выполняет исключительно расчет.
Не знает о пользовательском интерфейсе.
Не формирует документы.
Не работает с окнами программы.

Уровень хранения данных (Infrastructure)
Отвечает за:
сохранение проектов;
загрузку проектов;
экспорт;
импорт.
Не содержит математического алгоритма.

Уровень формирования документов (Documents)
Отвечает исключительно за подготовку:
печатной формы расчета;
Word-документа;
Excel-документа;
PDF-документа.
Не выполняет математических вычислений.

Пользовательский интерфейс (UI)
Отвечает только за взаимодействие пользователя с программой.
Не содержит математических формул.
Не содержит бизнес-логики.

1.4. Основные требования
Программа должна:
работать автономно без подключения к Интернету;
обеспечивать одинаковые результаты на всех поддерживаемых компьютерах;
поддерживать проекты любого размера;
обеспечивать сохранение всех версий проекта;
обеспечивать возможность полного перерасчета после изменения любых исходных данных.

1.5. Основной объект программы
Основной единицей работы программы является Проект расчета.
Проект объединяет:
сведения о должнике;
сведения о взыскателе (при необходимости);
основание расчета;
параметры расчета;
начисления задолженности;
произведенные оплаты;
изменения ключевой ставки;
результаты расчета;
историю изменений проекта;
сформированные документы.

1.6. Основной принцип хранения данных
Проект хранится в одном файле собственного формата.
Файл должен содержать:
исходные данные;
параметры программы;
историю изменений;
версии проекта;
результаты последнего расчета.

1.7. Основной принцип работы
Работа программы строится по следующему алгоритму:
Создание нового проекта либо открытие существующего.
Ввод исходных данных.
Автоматическое формирование событий расчета.
Выполнение математического расчета.
Проверка результата пользователем.
Формирование печатного документа.
Сохранение проекта.

1.8. Основной принцип сопровождения
Все изменения проекта должны выполняться путем изменения исходных данных с последующим полным автоматическим перерасчетом.
Ручное изменение результатов расчета не допускается.

1.9. Основной принцип расширяемости
Архитектура программы должна предусматривать возможность добавления новых типов событий, новых способов расчета, новых видов документов и новых форм отчетности без изменения уже реализованного математического ядра.

1.10. Требования к качеству
Программа должна соответствовать следующим требованиям:
математическая корректность;
повторяемость результатов;
модульная архитектура;
расширяемость;
сопровождаемость;
документированность;
тестируемость;
устойчивость к ошибкам пользователя;
сохранность данных проекта;
единообразие оформления документов.

Итог главы
Первая глава фиксирует фундаментальные принципы проекта. Все последующие разделы ТЗ должны соответствовать этим положениям и не могут им противоречить.

2. Термины и определения
Настоящий раздел устанавливает единые термины, используемые во всей документации проекта, исходном коде программы и пользовательском интерфейсе.

2.1. Проект
Проект — совокупность всех исходных данных, параметров расчета, результатов вычислений, истории изменений и сформированных документов, относящихся к одному расчету.
Проект является основной единицей хранения данных.
Каждый проект сохраняется в отдельном файле.

2.2. Расчет
Расчет — результат работы математического ядра программы, выполненный на основании исходных данных проекта.
Расчет всегда выполняется автоматически.
Ручное изменение результатов расчета не допускается.

2.3. Исходные данные
Исходные данные — сведения, вводимые пользователем до выполнения расчета.
К исходным данным относятся:
сведения о должнике;
сведения об основании расчета;
дата начала начислений;
дата окончания начислений;
график начислений;
произведенные оплаты;
используемая процентная ставка;
параметры расчета.

2.4. Начисление
Начисление — увеличение суммы задолженности в установленную дату на определенную сумму.
Начисление является событием расчета.
Начисление увеличивает задолженность.
Начисление не является оплатой.

2.5. График начислений
График начислений — последовательность начислений задолженности, автоматически формируемая программой либо заданная пользователем.
График может быть:
автоматическим;
измененным пользователем.
После автоматического формирования каждое начисление может быть изменено вручную.

2.6. Оплата
Оплата — поступление денежных средств, уменьшающее задолженность.
Каждая оплата является самостоятельным событием расчета.

2.7. Переплата
Переплата — состояние проекта, при котором сумма произведенных оплат превышает размер начисленной задолженности.
Переплата не образует отрицательной задолженности.
Проценты за пользование чужими денежными средствами в период существования переплаты не начисляются.
После возникновения новых начислений ранее внесенная переплата автоматически уменьшает вновь возникшую задолженность.
Если сумма переплаты полностью покрывает новое начисление, начисление процентов не производится.
Если после зачета переплаты остается непогашенная задолженность, проценты начисляются только на оставшуюся сумму начиная с момента возникновения просрочки.
Период существования переплаты не включается в таблицу расчета и не учитывается при определении количества дней просрочки.

2.8. Задолженность
Задолженность — сумма начислений, не погашенная произведенными оплатами.
В программе задолженность никогда не принимает отрицательных значений.
Минимальное значение задолженности равно нулю.

2.9. Просрочка
Просрочка — период наличия непогашенной задолженности, на которую начисляются проценты начиная с даты начисления по утвержденному графику.
Именно на период просрочки начисляются проценты.

2.10. Дата начисления и учет оплаты
Дата начисления — календарный день увеличения основного долга и начала начисления процентов на эту сумму. Для согласованного графика это 11 число месяца, в январе — 16 число.
Начало начисления процентов определяется автоматически в соответствии с правилами проекта.
Например:
ежемесячное начисление 11 числа — проценты начисляются с 11 числа включительно;
январское начисление 16 числа — проценты начисляются с 16 января включительно.
Выходные и праздничные дни не переносят дату начисления или оплаты. Оплата уменьшает расчетную задолженность со следующего календарного дня; день оплаты включается в расчет на сумму долга до этой оплаты.

2.11. Период расчета
Период расчета — непрерывный промежуток времени, в течение которого одновременно неизменны:
размер задолженности;
процентная ставка;
перечень событий.
Любое изменение хотя бы одного из указанных параметров завершает текущий период расчета и начинает новый.

2.12. Интервал расчета
Интервал расчета — строка таблицы расчета, соответствующая одному периоду расчета.
Каждый интервал содержит:
дату начала;
дату окончания;
количество календарных дней;
размер задолженности;
процентную ставку;
сумму начисленных процентов.

2.13. Событие расчета
Событие расчета — любое действие, изменяющее состояние расчета.
События подразделяются на:
начисление задолженности;
поступление оплаты;
изменение процентной ставки;
служебные события программы.
Все события обрабатываются в строгом порядке.

2.14. Приоритет события
При совпадении нескольких событий на одну дату программа обязана обработать их в следующем порядке:
изменение процентной ставки;
начисление задолженности;
поступление оплаты;
начало нового расчетного периода.
Изменение данного порядка не допускается.

2.15. Процентная ставка
Процентная ставка — величина, применяемая при расчете процентов.
Поддерживаются режимы:
ключевая ставка Банка России;
фиксированная ставка.

2.16. Ключевая ставка
Ключевая ставка — официальная ключевая ставка Банка России, действующая в соответствующий период.
Изменения ставки представляются в проекте отдельными событиями.

2.17. Фиксированная ставка
Фиксированная ставка — процентная ставка, задаваемая пользователем вручную и не изменяющаяся в течение расчета.

2.18. Расчет процентов
Расчет процентов — последовательное вычисление процентов отдельно для каждого интервала расчета.
Общий результат представляет собой сумму процентов всех интервалов.

2.19. Итог расчета
Итог расчета — итоговая сумма процентов за весь расчетный период.
Итог округляется по правилу AwayFromZero.

2.20. Проектная версия
Версия проекта — сохраненное состояние проекта на определенный момент времени.
Каждое сохранение проекта автоматически создает новую версию.
Количество версий не ограничивается.
Пользователь может открыть любую сохраненную версию проекта и сделать ее текущей.

2.21. История проекта
История проекта — журнал изменений, содержащий сведения обо всех сохраненных версиях проекта.
Для каждой версии фиксируются:
дата и время создания;
номер версии;
краткое описание автоматически определенных изменений.

2.22. Протокол расчета
Протокол расчета — служебный документ, предназначенный исключительно для проверки правильности расчета.
Протокол содержит:
все события;
расчетные интервалы;
промежуточные вычисления;
информацию о переплатах;
анализ по календарным годам;
сведения о версиях проекта;
диагностическую информацию.
Протокол не является официальным документом и не предназначен для представления в суд или иные организации.

2.23. Документ расчета
Документ расчета — официальный документ, формируемый программой для подписания и использования по назначению.
Документ содержит только сведения, необходимые для подтверждения результата расчета.
Диагностическая информация в документ не включается.

2.24. Основной отчет
Основной отчет — печатная форма расчета процентов.
Отчет должен быть:
лаконичным;
структурированным;
удобным для чтения;
пригодным для подписания.

2.25. Журнал изменений
Журнал изменений — документ, содержащий сведения обо всех изменениях программы между версиями.

2.26. Математическое ядро
Математическое ядро — программный модуль, выполняющий исключительно вычисления.
Ядро не зависит от пользовательского интерфейса, способов хранения данных и формирования документов.

2.27. Правило округления
Во всей программе используется единое правило округления AwayFromZero (классическое математическое округление):
0,004 → 0,00;
0,005 → 0,01;
1,235 → 1,24;
−1,235 → −1,24.
Использование иных способов округления не допускается.

Итог главы
Все приведенные определения являются обязательными для использования в технической документации, исходном коде программы и пользовательском интерфейсе. Использование терминов в ином значении не допускается.

3. Функциональные требования
3.1. Общие положения
Программа LexPercent Pro предназначена для автоматизированного расчета процентов за пользование чужими денежными средствами, формирования официальных документов, хранения проектов и ведения истории изменений.
Все вычисления выполняются автоматически на основании исходных данных проекта.
Пользователь не имеет возможности изменять результаты расчета вручную.
Изменение результата возможно только путем изменения исходных данных с последующим автоматическим перерасчетом.

3.2. Основные функции программы
Программа должна обеспечивать выполнение следующих функций:
создание нового проекта;
открытие существующего проекта;
сохранение проекта;
автоматическое создание новой версии проекта при сохранении;
копирование проекта;
автоматический перерасчет;
формирование официального документа расчета;
формирование протокола расчета;
экспорт документов;
импорт данных (при последующем развитии проекта);
просмотр истории версий;
восстановление любой сохраненной версии проекта.

3.3. Создание проекта
При создании нового проекта пользователь вводит исходные данные.
Проект должен содержать:
Общие сведения
номер расчета;
дата расчета;
организация;
руководитель (для блока «УТВЕРЖДАЮ»);
исполнитель;
основание расчета.
Сведения о должнике
Ф.И.О.;
дополнительные сведения (при необходимости).
Параметры расчета
дата начала начислений;
дата окончания начислений;
дата окончания расчета;
режим начисления процентов;
тип процентной ставки;
параметры графика начислений.

3.4. Копирование проекта
Пользователь может создать новый проект путем копирования существующего.
При копировании автоматически переносятся:
организация;
руководитель;
исполнитель;
параметры расчета;
график начислений;
процентная ставка;
настройки оформления документа.
По умолчанию автоматически очищаются:
оплаты;
история проекта;
результаты расчета;
версии проекта.
Фамилия должника, основание расчета и иные сведения могут быть изменены пользователем после создания копии.

3.5. Автоматическое формирование графика начислений
Программа должна поддерживать автоматическое создание графика начислений.
Пользователь задает:
число месяца;
сумму ежемесячного начисления.
После этого программа автоматически формирует начисления на весь расчетный период.
Каждое автоматически созданное начисление может быть изменено пользователем.
Допускается изменение:
даты;
суммы;
удаление начисления;
добавление нового начисления.

3.6. Окончание графика начислений
Пользователь может указать дату окончания начислений.
После этой даты новые начисления автоматически не создаются.
При этом расчет процентов продолжается до даты окончания расчета.
В течение данного периода расчетная задолженность остается неизменной до следующего календарного дня после оплаты либо до даты действия другого события.

3.7. Виды процентной ставки
Программа должна поддерживать два режима расчета:
Ключевая ставка Банка России
Процентная ставка изменяется автоматически в соответствии с таблицей ставок, введенной пользователем.

Фиксированная ставка
Пользователь самостоятельно задает значение процентной ставки.
Фиксированная ставка применяется ко всем расчетным периодам.

3.8. Оплаты
Пользователь может добавить неограниченное количество оплат.
Для каждой оплаты указываются:
дата оплаты;
сумма оплаты.
Все оплаты автоматически сортируются по дате.

3.9. Правила изменения задолженности
Начисления увеличивают задолженность.
Оплаты уменьшают задолженность.
Если сумма произведенной оплаты превышает размер задолженности, образуется остаток предварительной оплаты (переплата).
Переплата автоматически переносится на последующие начисления.
В период, когда задолженность полностью отсутствует вследствие переплаты:
проценты не начисляются;
просрочка отсутствует;
соответствующие периоды не включаются в основную таблицу расчета.
После возникновения нового начисления ранее образовавшаяся переплата автоматически уменьшает его размер.
Если переплата полностью покрывает начисление, проценты не начисляются.
Если после зачета переплаты остается непогашенная сумма, проценты начисляются только на эту сумму с момента возникновения просрочки.

3.10. Автоматический перерасчет
Любое изменение исходных данных автоматически требует полного перерасчета проекта.
Перерасчет производится после изменения:
начислений;
оплат;
ставок;
дат;
параметров расчета.
Результаты предыдущего расчета не изменяются вручную.

3.11. События расчета
Все вычисления строятся исключительно на основании событий.
Поддерживаются события следующих типов:
начисление задолженности;
оплата;
изменение процентной ставки;
служебные события.
Все события автоматически сортируются.

3.12. Приоритет обработки событий
При совпадении нескольких событий на одну дату применяется следующий порядок:
изменение процентной ставки;
начисление задолженности;
оплата;
начало нового расчетного периода.
Данный порядок является обязательным.

3.13. Итоговые показатели расчета
По окончании расчета программа должна определить:
общую сумму начислений;
общую сумму оплат;
итоговую сумму процентов;
количество расчетных периодов;
дату начала расчета;
дату окончания расчета.

3.14. Количество дней просрочки
Программа должна определять общее количество календарных дней, за которые были начислены проценты за пользование чужими денежными средствами.
Периоды отсутствия задолженности вследствие переплаты в расчет не включаются.
Данный показатель отображается:
в основном документе расчета;
в протоколе расчета.

3.15. Итоговая сумма процентов
Итоговая сумма процентов определяется как сумма процентов всех расчетных периодов.
Округление производится только по утвержденному правилу AwayFromZero.

3.16. Анализ погашения начислений
Для каждого календарного года программа должна определять:
сумму начислений за год;
сумму оплат, относимых на начисления данного года;
процент погашения начислений данного года.
При расчете процента погашения учитываются только начисления и оплаты соответствующего календарного года.
Остаток задолженности предыдущих лет в расчете данного показателя участия не принимает.
Данный анализ отображается только в протоколе расчета.

3.17. Основной документ расчета
Основной документ предназначен для подписания и использования по назначению.
Документ должен содержать только сведения, необходимые для подтверждения произведенного расчета.
Любая аналитическая, диагностическая и служебная информация в основной документ не включается.

3.18. Основная таблица расчета
Для каждого расчетного периода отображаются:
период полностью (например: 01.01.2026–14.01.2026);
количество календарных дней;
размер задолженности;
процентная ставка;
сумма процентов.
В конце таблицы выводится строка «Итого».

3.19. Протокол расчета
Протокол предназначен исключительно для проверки правильности вычислений.
Он содержит:
все события;
журнал изменения задолженности;
расчетные интервалы;
математические формулы;
анализ по календарным годам;
сведения о переплатах;
служебную информацию.
Протокол не предназначен для подписания.

3.20. История версий
Каждое сохранение проекта автоматически создает новую версию.
Количество версий не ограничивается.
Пользователь может:
просмотреть список версий;
открыть любую версию;
сделать выбранную версию текущей.
История изменений хранится вместе с проектом.

3.21. Поиск проектов
Программа должна обеспечивать поиск проектов по следующим параметрам:
номер расчета;
фамилия должника;
дата расчета;
дата последнего изменения.
Поиск по основанию расчета не предусматривается.

3.22. Проверка математического алгоритма
Программа должна содержать раздел «Справка → Тест расчетов», предназначенный для проверки корректности математического ядра.
При запуске тестирования выполняются все встроенные эталонные тесты.
Результаты тестирования отображаются пользователю в виде отчета.

3.23. Требования к устойчивости
Программа должна предотвращать:
потерю данных;
повреждение проекта при сохранении;
появление отрицательной задолженности;
ручное изменение результатов расчета;
математически некорректные вычисления.
При возникновении ошибки пользователь получает понятное сообщение с описанием проблемы.

Итог главы
Настоящий раздел определяет полный состав функциональных требований к программе и является основой для реализации пользовательского интерфейса, математического ядра и механизмов хранения данных. Любая функциональность, реализуемая в программе, должна соответствовать требованиям настоящего раздела.
4. Математическая модель расчета
4.1. Общие положения
Настоящий раздел определяет математическую модель, применяемую программой LexPercent Pro.
Все вычисления производятся автоматически.
Пользователь не участвует в выполнении вычислений и не может изменять промежуточные либо итоговые результаты.
Все результаты являются следствием обработки исходных данных в соответствии с настоящим разделом.

4.2. Основной принцип
Расчет представляет собой последовательную обработку событий, изменяющих состояние проекта.
К событиям относятся:
начисление задолженности;
поступление оплаты;
изменение процентной ставки;
окончание расчетного периода.
Расчет производится путем последовательного перехода от одного события к следующему.

4.3. Исходное состояние
Перед началом расчета программа формирует начальное состояние проекта.
Начальное состояние включает:
текущую задолженность;
текущую процентную ставку;
остаток предварительной оплаты (при наличии);
текущую дату расчета.

4.4. Событийная модель
Все изменения проекта рассматриваются как последовательность событий.
Каждое событие обладает следующими обязательными свойствами:
дата;
тип события;
значение;
описание (необязательно).
После формирования списка событий он становится неизменяемым до завершения расчета.

4.5. Сортировка событий
Перед выполнением расчета программа сортирует все события:
по дате действия события в расчете: для начисления и ставки — указанная дата, для оплаты — следующий календарный день после фактической оплаты;
при совпадении даты — по приоритету.
Приоритет обработки событий:
изменение процентной ставки;
начисление задолженности;
поступление оплаты;
завершение расчетного периода.
Изменение порядка обработки не допускается.

4.6. Формирование расчетных периодов
После сортировки событий программа автоматически разбивает весь расчетный период на интервалы.
Новый интервал начинается при любом из следующих условий:
изменилась задолженность;
изменилась процентная ставка;
поступила оплата;
выполнено начисление;
достигнута дата окончания расчета.
Каждый интервал является самостоятельной единицей вычисления.

4.7. Неизменность параметров интервала
В пределах одного расчетного интервала остаются неизменными:
сумма задолженности;
процентная ставка;
количество календарных дней.
Если изменяется хотя бы один параметр, текущий интервал завершается.

4.8. Правило начисления задолженности
В дату начисления основной долг увеличивается на величину начисления. Проценты на непогашенную часть начисления рассчитываются с этой же даты, включая первое начисление.
Начисление не оказывает влияния на уже рассчитанные интервалы.

4.9. Правило обработки оплаты
Дата фактической оплаты сохраняется в исходных данных. Для расчета процентов уменьшение задолженности на величину оплаты применяется со следующего календарного дня. До этого уменьшения, включая день оплаты, проценты начисляются на прежнюю сумму задолженности.
Если оплата превышает текущую задолженность, задолженность принимается равной нулю.
Неиспользованная часть оплаты образует остаток предварительной оплаты (переплату).

4.10. Правило переплаты
Переплата автоматически переносится на последующие начисления.
До полного использования переплаты:
задолженность считается отсутствующей;
проценты не начисляются;
просрочка отсутствует;
интервалы расчета не формируются.
После появления нового начисления программа автоматически уменьшает его на величину имеющейся переплаты.
Проценты начисляются только на непогашенную часть начисления.

4.11. Правило возникновения просрочки
Просрочка для целей расчетной модели начинается в дату начисления при наличии непогашенной задолженности, в соответствии с утвержденным эталоном.
Если задолженность полностью отсутствует вследствие произведенной оплаты либо переплаты, просрочка отсутствует.

4.12. Начало начисления процентов
Проценты начинают начисляться в дату начисления включительно: для согласованного графика с 11 числа, в январе с 16 числа. Перенос начала на 12 или 17 число не применяется.
Например:
Дата начисления | Начало начисления процентов
11 число месяца | с 11 числа включительно
16 января | с 16 января включительно
Настоящее правило применяется автоматически.

4.13. Окончание начисления процентов
Начисление процентов прекращается:
со следующего календарного дня после полной оплаты задолженности;
после даты окончания расчета; сама дата окончания включается в расчет;
при полном покрытии задолженности переплатой.

4.14. Изменение процентной ставки
При изменении процентной ставки текущий расчетный интервал завершается.
Следующий интервал начинается с новой ставки.
Размер задолженности при этом не изменяется.

4.15. Изменение задолженности
Начисление завершает предыдущий интервал накануне даты начисления. Оплата завершает интервал в день фактической оплаты; следующий интервал с уменьшенным долгом начинается на следующий календарный день.
Новый интервал начинается с обновленным размером задолженности.

4.16. Расчет процентов за интервал
Для каждого интервала программа определяет:
дату начала;
дату окончания;
количество календарных дней;
сумму задолженности;
процентную ставку.
После этого вычисляется сумма процентов за данный интервал.
Формула расчета определяется выбранным режимом расчета и требованиями законодательства.
Математическая формула реализуется в программном коде единообразно для всех интервалов.
4.16.1. Формула расчета процентов
Для каждого расчетного интервала проценты рассчитываются по формуле:
Проценты=Сумма задолженности×Процентная ставка×(Количество дней/Количество дней в году)×100
где:
Сумма задолженности — размер задолженности в данном расчетном интервале;
Процентная ставка — действующая ставка в процентах годовых;
Количество дней — количество календарных дней расчетного интервала;
Количество дней в году определяется согласно пункту 4.16.2.

4.16.2. Количество дней в году
При расчете используется фактическое количество календарных дней в соответствующем календарном году.
Используются следующие значения:
обычный год — 365 дней;
високосный год — 366 дней.
Если расчетный интервал пересекает границу календарного года, программа автоматически разделяет его на отдельные интервалы по каждому календарному году.
Таким образом, в пределах одного расчетного интервала всегда используется только одно значение количества дней в году.

4.16.3. Правила учета дат
При расчете применяются следующие правила:
первый день просрочки включается в расчет;
последний день расчетного интервала включается в расчет;
день, предшествующий возникновению просрочки, в расчет не включается;
периоды отсутствия задолженности в расчет не включаются;
день оплаты включается в расчет на сумму задолженности до оплаты; оплаченная сумма исключается из базы начисления процентов со следующего календарного дня.
Эти правила являются едиными для всех расчетов и не могут изменяться пользователем.

4.16.4. Правила округления
Во всех расчетах программы применяется единое правило округления AwayFromZero.
Округление выполняется до двух знаков после запятой.
Промежуточные вычисления выполняются с максимально возможной точностью типа decimal, после чего результат расчетного интервала округляется до двух знаков.
Итоговая сумма процентов определяется как сумма округленных значений всех расчетных интервалов.

4.16.5. Неизменность математической модели
Настоящие правила являются обязательными для всех версий программы.
Любое изменение:
формулы расчета;
порядка учета календарных дней;
порядка учета дат;
правил округления
допускается только путем выпуска новой версии технического задания и новой версии программы.


4.17. Итог расчета
Итоговая сумма процентов определяется как сумма процентов всех расчетных интервалов.
Каждый интервал рассчитывается независимо.

4.18. Правило округления
Во всех вычислениях используется единое правило округления AwayFromZero.
Промежуточные значения сохраняются с максимальной точностью, необходимой для корректного выполнения вычислений.
Округление выполняется только в случаях, предусмотренных алгоритмом расчета.

4.19. Количество дней просрочки
Общее количество дней просрочки определяется как сумма календарных дней всех интервалов, по которым производилось начисление процентов.
Интервалы отсутствия задолженности в расчет не включаются.

4.20. Основные математические инварианты
Во время выполнения расчета должны соблюдаться следующие условия:
задолженность не может быть отрицательной;
переплата не может быть отрицательной;
расчетные интервалы не пересекаются;
каждый календарный день относится только к одному интервалу;
изменение ставки не изменяет задолженность;
изменение задолженности не изменяет процентную ставку;
все события обрабатываются только один раз;
результаты завершенных интервалов повторно не пересчитываются в рамках одного запуска алгоритма.

4.21. Повторяемость расчета
При одинаковых исходных данных программа обязана получать полностью идентичный результат независимо от:
даты выполнения расчета;
компьютера пользователя;
версии операционной системы;
региональных настроек.

4.22. Перерасчет
При изменении любых исходных данных:
начислений;
оплат;
ставок;
дат;
параметров проекта,
ранее полученный результат аннулируется.
После этого выполняется полный перерасчет проекта с самого начала.
Частичный перерасчет не допускается.

4.23. Детерминированность алгоритма
Алгоритм расчета является полностью детерминированным.
При одинаковом наборе событий последовательность вычислений всегда одинакова.
Использование случайных величин, эвристик либо зависимых от времени вычислений не допускается.

4.24. Контроль корректности
После завершения расчета программа автоматически выполняет внутреннюю проверку результатов.
Контролируются:
отсутствие отрицательной задолженности;
отсутствие отрицательной переплаты;
отсутствие пересекающихся интервалов;
непрерывность расчетного периода;
соответствие итоговой суммы процентов сумме процентов всех интервалов.
При обнаружении нарушения расчет считается ошибочным и результаты пользователю не предоставляются.

4.25. Независимость математического ядра
Математическое ядро не должно зависеть:
от пользовательского интерфейса;
от хранения данных;
от формата документов;
от способа печати;
от экспорта.
Ядро получает на вход только модель проекта и возвращает только результат расчета.

8. Хранение данных
8.1. Общие положения

Каждый проект сохраняется в отдельном файле собственного формата.

.lpp
(LexPercent Project)

идентификатор проекта;
номер расчета;
дата создания;

сведения об организации;

история версий;
настройки оформления документа.
После открытия файла проект должен полностью восстанавливаться в том состоянии, в котором он находился на момент последнего сохранения.

8.4. Независимость проекта
Каждый файл проекта является полностью независимым.
Для открытия проекта не требуется наличие других файлов.
Все сведения, необходимые для выполнения расчета, должны храниться внутри проекта.

Глобальные настройки программы не включаются в файл проекта.

руководитель по умолчанию;
параметры первого шаблона документа;
каталог хранения проектов;
параметры экспорта;
пользовательские настройки интерфейса.

При первом запуске автоматически открывается мастер первоначальной настройки.

Программа должна поддерживать автоматическое сохранение проекта.
Интервал автосохранения настраивается пользователем.
По умолчанию рекомендуется использовать интервал 5 минут.
Автосохранение не создает новую версию проекта. Оно предназначено исключительно для защиты данных от потери при аварийном завершении работы.

8.8. Сохранение проекта
При выполнении команды «Сохранить»:
выполняется перерасчет (если имеются изменения);
создается новая версия проекта;
проект записывается на диск.
Если исходные данные не изменились, новая версия проекта не создается.

8.9. История версий
История версий хранится внутри файла проекта.
Каждая версия представляет собой полный снимок проекта на момент сохранения и включает:
все исходные данные;
параметры расчета;
список событий;
результаты расчета;
настройки оформления документа.
Количество версий не ограничивается.

8.10. Работа с версиями
Пользователь может:
просмотреть список всех сохраненных версий;
открыть любую версию для просмотра;
восстановить любую версию в качестве текущей;
сравнить две любые версии между собой.
При восстановлении версии:
выбранная версия становится текущей;
автоматически создается новая версия, фиксирующая факт восстановления;
исходные версии остаются неизменными.

Программа должна обеспечивать наглядное сравнение двух любых версий проекта.
При сравнении отображаются изменения:
общих сведений проекта;
параметров расчета;
начислений;
оплат;
процентных ставок;
результатов расчета;
итоговой суммы процентов;
количества дней просрочки.
Изменения должны быть представлены в удобной для анализа форме с выделением добавленных, удаленных и измененных данных.

При копировании проекта создается новый независимый файл.
По умолчанию:
Сохраняются:

руководитель;
параметры расчета;
график начислений;
параметры документа;
шаблон оформления.
Очищаются:

результаты расчета;
история версий.
Пользователь может изменить фамилию должника, номер расчета и другие сведения перед сохранением нового проекта.

8.13. Последние проекты
Программа хранит список последних открытых проектов.
Для каждого проекта отображаются:
номер расчета;

дата последнего изменения.

№459 — Петров
№460 — Сидоров

Программа предоставляет возможность создать резервную копию проекта.
Резервная копия представляет собой обычный файл проекта и может быть открыта на любом компьютере с установленной программой.

8.15. Совместимость версий
Программа должна обеспечивать открытие проектов, созданных предыдущими версиями программы, если это возможно без потери данных.
При необходимости выполняется автоматическая миграция формата проекта.
Все действия по миграции фиксируются в журнале проекта.

8.16. Защита от повреждения файла
Сохранение проекта должно выполняться по безопасной схеме:
запись во временный файл;
проверка успешности записи;
замена исходного файла.
Это предотвращает потерю данных при отключении питания или аварийном завершении программы во время сохранения.

8.17. Переносимость проекта
Файл проекта не должен содержать абсолютных путей к файлам пользователя или иных данных, препятствующих переносу проекта на другой компьютер.
Проект должен открываться независимо от расположения файла.

Все текстовые данные сохраняются в кодировке UTF-8.
Это обеспечивает корректное хранение символов русского языка и совместимость с современными операционными системами.

8.19. Ограничения
Файл проекта не должен содержать:
временные данные пользовательского интерфейса;
журналы отладки;
диагностические сообщения;
кэшированные данные.
Хранятся только сведения, необходимые для восстановления проекта и выполнения расчета.

8.20. Требования к надежности хранения
После успешного сохранения программа должна гарантировать, что:
файл проекта может быть открыт;
все данные проекта восстановятся без изменений;
результаты расчета будут совпадать с результатами до сохранения.

8.21. Независимость хранения
Механизм хранения данных не должен зависеть:
от пользовательского интерфейса;
от математического ядра;
от механизма формирования документов.
Он должен обеспечивать исключительно запись и чтение данных проекта.
9. Тестирование и контроль корректности
9.1. Общие положения
Программа LexPercent Pro должна обеспечивать воспроизводимость и корректность результатов расчета.
Контроль правильности работы осуществляется посредством автоматического выполнения набора эталонных тестов.
Каждая новая версия программы должна успешно проходить все тесты до выпуска.

9.2. Виды тестирования
В проекте применяются следующие виды тестирования:
модульное тестирование;
интеграционное тестирование;
функциональное тестирование;
регрессионное тестирование;
тестирование производительности.

9.3. Эталонные тесты
Основой проверки математического ядра являются эталонные тесты.
Каждый тест содержит:
описание задачи;
исходные данные;
ожидаемый результат;
подробную таблицу расчета;
итоговую сумму процентов;
количество дней просрочки.
После выполнения теста программа автоматически сравнивает фактический результат с эталонным.

9.4. Структура тест-кейса
Каждый тест-кейс включает:
уникальный идентификатор (например, TC-001);
наименование;
описание сценария;
исходные данные;
ожидаемый результат;
критерии успешного прохождения.

9.5. Минимальный набор тестов
В состав проекта должны входить тесты, проверяющие:
одно начисление без оплат;
одно начисление с полной оплатой;
одно начисление с частичной оплатой;
несколько начислений;
несколько оплат;
изменение ключевой ставки;
фиксированную ставку;
переплату;
отсутствие задолженности;
начисления после окончания графика;
переход через високосный год;
переход через несколько календарных лет;
изменение срока оплаты января;
копирование проекта;
восстановление версии;
сравнение версий.

9.6. Проверка математического ядра
При выполнении тестов проверяются:
корректность формирования интервалов;
правильность определения количества дней;
правильность применения процентной ставки;
правильность учета оплат;
корректность обработки переплаты;
правильность итоговой суммы процентов;
правильность количества дней просрочки.

9.7. Контроль округления
Для каждого расчетного интервала проверяется:
корректность промежуточных вычислений;
правильность округления до двух знаков после запятой;
соответствие итоговой суммы процентов сумме всех интервалов.

9.8. Проверка календаря
Автоматически проверяются:
обычные годы (365 дней);
високосные годы (366 дней);
переход между календарными годами;
различное количество дней в месяцах;
февраль високосного года.

9.9. Проверка событийной модели
Проверяется правильность обработки:
начислений;
оплат;
изменений процентной ставки;
автоматических начислений;
окончания периода начислений;
окончания расчетного периода.

9.10. Проверка истории версий
Автоматически проверяются:
создание новой версии при сохранении;
отсутствие новой версии при отсутствии изменений;
восстановление любой версии;
сохранность всех предыдущих версий;
корректность сравнения двух версий.

9.11. Проверка формирования документов
Для каждого поддерживаемого формата (PDF, DOCX, XLSX) проверяется:
наличие всех обязательных разделов;
корректность итоговых сумм;
соответствие данных результатам расчета;
правильность оформления таблицы;
корректность отображения блока «УТВЕРЖДАЮ» (если он включен).

9.12. Проверка пользовательского интерфейса
Проверяется:
корректное отображение данных проекта;
правильная работа поиска;
работа фильтрации;
добавление, изменение и удаление событий;
работа предварительного просмотра;
корректность изменения параметров оформления документа.

9.13. Производительность
Программа должна обеспечивать выполнение полного расчета в разумное время даже для проектов с большим количеством событий.
Также проверяется скорость:
открытия проекта;
сохранения проекта;
восстановления версии;
экспорта документов.

9.14. Регрессионное тестирование
Перед выпуском каждой новой версии автоматически выполняются все эталонные тесты.
Изменение результата хотя бы одного теста считается регрессией.
Выпуск версии с регрессией не допускается до выяснения причин и устранения проблемы.

9.15. Контроль качества
Результаты тестирования оформляются в виде отчета.
Отчет должен содержать:
дату выполнения;
версию программы;
перечень выполненных тестов;
результаты прохождения;
перечень обнаруженных ошибок (при наличии).

9.16. Журнал изменений
Каждая версия программы сопровождается журналом изменений (ChangeLog).
Журнал должен содержать:
номер версии;
дату выпуска;
перечень новых функций;
перечень исправленных ошибок;
изменения в техническом задании (при наличии).

9.17. Критерии готовности версии
Версия программы считается готовой к выпуску только при выполнении следующих условий:
успешно пройдены все эталонные тесты;
отсутствуют критические ошибки;
результаты расчета соответствуют ожидаемым;
документация обновлена;
журнал изменений актуален.

Итог главы
Настоящий раздел определяет обязательные требования к проверке корректности работы программы. Любая версия LexPercent Pro должна проходить полный цикл автоматизированного тестирования перед использованием или выпуском.
Глава 10. Архитектура системы
Эта глава завершает техническое задание и определяет требования к внутренней архитектуре программы без привязки к конкретной реализации.
10.1. Общие положения
Программа LexPercent Pro строится по модульному принципу.
Каждый модуль отвечает за строго определенную область ответственности.
Модули должны быть максимально независимы друг от друга.
Изменение одного модуля не должно требовать изменения остальных, если не изменяется публичный интерфейс взаимодействия.

10.2. Основные модули
Архитектура программы включает следующие модули:
LexPercent.Domain — модель предметной области;
LexPercent.Core — математическое ядро расчета;
LexPercent.Documents — формирование документов;
LexPercent.Storage — сохранение и загрузка проектов;
LexPercent.UI — пользовательский интерфейс;
LexPercent.Tests — автоматическое тестирование.
Каждый модуль должен иметь четко определенную область ответственности.

10.3. Принцип разделения ответственности
В программе применяется принцип единственной ответственности (Single Responsibility Principle).
Каждый модуль выполняет только свою задачу:
математическое ядро не работает с интерфейсом;
интерфейс не выполняет вычислений;
модуль документов не изменяет данные проекта;
модуль хранения не содержит вычислительной логики.

10.4. Взаимодействие модулей
Взаимодействие модулей осуществляется только через публичные интерфейсы.
Прямой доступ к внутренней реализации других модулей не допускается.
Это обеспечивает возможность изменения реализации без нарушения работы системы.

10.5. Независимость пользовательского интерфейса
Пользовательский интерфейс должен быть полностью отделен от математического ядра.
Замена технологии интерфейса (например, переход на новую версию Avalonia или другую платформу) не должна требовать изменения алгоритмов расчета.

10.6. Независимость математического ядра
Математическое ядро должно работать исключительно с объектами предметной области.
Оно не должно зависеть от:
пользовательского интерфейса;
механизмов хранения;
генерации документов.
Это позволит использовать одно и то же ядро для любых вариантов интерфейса.

10.7. Генерация документов
Формирование документов выполняется только на основании результата расчета.
Модуль документов не имеет права изменять исходные данные проекта или результаты вычислений.

10.8. Хранение данных
Модуль хранения отвечает только за:
сохранение проекта;
загрузку проекта;
работу с версиями проекта.
Он не выполняет вычислений и не изменяет бизнес-логику.

10.9. Расширяемость
Архитектура должна предусматривать возможность добавления новых возможностей без переработки существующих модулей.
В частности, в будущем может быть реализована поддержка:
новых видов процентов;
новых форм документов;
дополнительных форматов экспорта;
новых отчетов.
При этом существующая функциональность должна оставаться неизменной.

10.10. Производительность
Архитектура должна обеспечивать эффективную работу с проектами любого разумного объема.
Расчет должен выполняться без заметных задержек для пользователя.
Длительные операции выполняются с отображением индикатора выполнения.

10.11. Надежность
Система должна обеспечивать:
корректную обработку ошибок;
сохранность данных пользователя;
невозможность повреждения проекта при аварийном завершении работы.

10.12. Сопровождаемость
Исходный код программы должен быть организован таким образом, чтобы внесение изменений было максимально простым и безопасным.
При добавлении новой функциональности не должно возникать необходимости изменять уже протестированные компоненты без объективной необходимости.

10.13. Документирование кода
Публичные классы, методы и интерфейсы должны сопровождаться комментариями, достаточными для понимания их назначения разработчиками проекта.
Документирование должно поддерживаться в актуальном состоянии при изменении функциональности.

10.14. Контроль качества
Перед включением изменений в основную ветку разработки должны быть выполнены:
успешная сборка проекта;
прохождение автоматических тестов;
проверка отсутствия критических ошибок.

10.15. Требования к платформе
Первая версия программы разрабатывается для операционной системы Microsoft Windows.
Архитектура не должна препятствовать возможному выпуску версий для других операционных систем в будущем.

10.16. Итоговые требования
Архитектура программы должна обеспечивать:
надежность;
расширяемость;
сопровождаемость;
воспроизводимость результатов расчета;
независимость модулей;
стабильную работу на протяжении всего жизненного цикла проекта.
